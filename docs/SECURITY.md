# Security policy

Tier Together treats Discord and Ludicord’s verified session as the source of identity. Authenticated HTTP routes and WebSockets use the server-provided session context, never a user, guild, application, or Activity-instance identifier sent in a browser payload. Production requires signed Discord proxy requests and verified Activity instances, and both checks fail closed when their server-side credentials are absent or invalid. Realtime rooms are keyed from those verified claims, while individual commands are validated again for payload shape, revision, phase, and host authority.

Secrets do not belong in this repository. Keep Discord credentials and the session key in an ignored local file during development and in the hosting provider’s secret store in production. The committed example contains empty values only. The production build includes Ludicord’s client-secret scan, but that is a final guard rather than a substitute for careful handling. If a credential is ever committed, pasted into an issue, printed in a public log, or otherwise exposed, rotate it immediately; rewriting Git history does not make an exposed credential trustworthy again.

The application stores active boards, votes, participant details, custom item images, and generated exports only in process memory. Empty rooms expire, server restarts clear active sessions, and each participant can have only one generated export waiting at a time. Export links use high-entropy tokens, expire after five minutes, are never cached, and serve with restrictive browser headers. This design keeps the data footprint small, but it also means the service must remain on one replica until shared realtime coordination is added deliberately.

Please report a suspected vulnerability privately through GitHub’s security advisory feature for this repository. Include the affected route or action, the impact you observed, and the smallest reproduction you can provide, but do not include real user data or active credentials. Avoid public issues for unresolved vulnerabilities. Maintainers should acknowledge a useful report, reproduce it against the current release, prepare a narrow fix, and coordinate disclosure after affected credentials or deployments have been secured.

For production operation, allow only the actual public hostname, keep HTTPS termination enabled, leave HTTP and WebSocket traffic on the same origin, deploy from the lockfile, and use one process replica. Review dependency advisories regularly, test the Activity inside Discord rather than only in a browser, and keep Discord, Railway, and GitHub accounts protected with multifactor authentication.
